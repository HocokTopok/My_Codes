# Pool Allocator

В этой задаче вам предстоит реализовать свой аллокатор - упрощенный
аналог `std::pmr::unsynchronized_pool_resource`.

## Архитектура аллокатора

Наиболее подробное описание можно составить ознакомившись с
[cppreference][1]. Здесь приведем лишь краткое описание
архитектуры:

- Ваш ресурс (аллокатор) состоит из нескольких pool'ов, которые
  отвечают за аллокации разных размеров
- Каждый pool отвечает за выделение фиксированного размера и
  состоит из растущего числа чанков, каждый из которых разделен на
  бакеты
- Чанки, которые уже выделены для определенного pool'а не
  возвращаются исходному аллокатору пока ваш аллокатор не уничтожен,
  даже если все бакеты внутри чанка свободны
- Размеры бакетов в каждом последующем pool'е растут
  экспоненциально, пока не достигнут определенного значения, начиная
  с которого аллокации не используют pool'ы

## Детали реализации

Важнейшим свойством, которое вам нужно обеспечить, является
совместимость со стандартными контейнерами. Для полиморфных
аллокаторов это достигается публичным наследованием
`std::memory_resource` и реализацией его виртуальных методов.

Ваш аллокатор должен принимать `std::pmr::pool_options` в качестве
шаблонного аргумента и использовать его для изменения логики
работы механизма pool'ов.

Аллокатор должен иметь конструктор по-умолчанию, который
использует `std::pmr::get_default_resource` для выделения чанков и
конструктор от `std::pmr::memory_resource*`, который для этого
использует предоставленный ресурс.

Нужно уметь подчищать за пользователем утечки памяти. Даже если
пользователь забыл вызвать `deallocate` на какой-то выделенной
памяти, деструктор аллокатора все равно должен уметь правильно
освободить её.

Хорошим тоном для аллокаторов является возможность обнаруживать
некорректные запросы освобождения памяти. Вам необходимо
реализовать проверки для следующих ошибок:

- Попытка освободить бакет, который является свободным (для
  аллокаций, которые используют мехнизм pool'ов)
- Вызов `deallocate` на указателе, выравнивание которого меньше
  чем `align`
- Вызов `deallocate` с аргументом `size`, который отличается от
  `size`, который был передан в `allocate`

## Инварианты

Для удобства тестирования и из-за других причин вашей реализации
выставляются некоторые требования, которые, возможно, излишне
сужают перечень валидных решений для этой задачи:

- Для поддержки внутренних структур аллокатора запрещается
  выделять и освобождать дополнительную память после завершения
  исполнения его конструктора
- Стандарт трактует значения полей в `std::pmr::pool_options` как
  рекоммендации, а не требования, однако от вас ожидается строгое
  соответствие этим настройкам
- Более того, вам гарантируется, что поле `max_blocks_per_chunk`
  в `std::pmr::pool_options` не равно 0, а поле
  `largest_required_pool_block` является степенью 2
- Экспоненциальный рост размера бакетов можно обеспечить разными
  способами, однако от вас требуется использовать **постоянный
  growth factor равный 2**
- Время работы выделения и освобождения памяти вашим аллокатором
  должно быть гарантированным **O(1)** (не зависит от числа
  выделенных объектов)
- При обнаружении ошибки в `deallocate` реальные аллокаторы обычно
  вызывают `std::abort` для обеспечения безопасности, однако от
  вас требуется бросать исключение, унаследованное от
  `std::exception`.

## Что **НЕ** нужно делать

Большинство аллокаторов поддерживают конкурентные вызовы из
нескольких потоков (в этом состоит разница между
`std::pmr::synchronized_pool_resource` и
`std::pmr::unsynchronized_pool_resource`), однако от вас этого не
требуется.

Ваш аллокатор может не поддерживать аллокации нулевого размера.

Вам разрешается не поддерживать типы с выравниванием больше чем
`alignof(size_t)`.
